# Provider Ports (Draft v0.1)

Status: draft. Companion to `function-strips-plan.md` (section 11 has the rules). This file lists the ports, the decisions each port must fix, and the adapters planned.

Hosting target for the web and API: Cloudflare Workers through the OpenNext adapter. Other parts (database, ingestion, background work) are chosen per app. Items marked "verify" depend on current Cloudflare or provider documentation that has not been checked yet.

## 1. How to read this file

- A **port** is an interface in `src/ports/`, written in domain terms.
- An **adapter** is an implementation in `src/adapters/<port>/<provider>/`.
- Every port has at least a real adapter and an in-memory adapter, and one contract test suite that runs against all adapters.
- Provider errors are mapped to `ErrorKind` inside the adapter. Each adapter has a tested mapping table.
- Ports in this file belong to the skeleton. Repositories (`UserReader`, `OrderWriter`) are app-specific. Each app defines its own, following the database port rules below.

## 3. Rules every port follows

1. **Domain types only.** No rows, driver objects, SDK response shapes, or provider IDs in signatures.
2. **Errors as `Result`.** Adapters return `Result` with an `ErrorKind`, or throw and let `step()` convert the exception to `unexpected`. Nothing returns an error as a string value.
3. **Semantics written down.** Each port section below lists the decisions that differ between providers.
4. **Capability flags for gaps.** If a provider lacks a feature the port offers, the adapter says so through a documented capability flag. The contract test skips the matching cases, and the strip checks the flag.
5. **Provider-only features** go in a separate optional port.
6. **Read and write are separate** where permissions matter (`UserReader`, `UserWriter`), so capability injection can give a step only what it needs.

## 4. Decisions per port

### Database

Skeleton port: atomic writes, migrations, and health check. App repositories are built on it.

- **IDs**: generated by the application (`IdGenerator`), stored as text. No database auto-increment IDs in signatures, since providers differ.
- **Timestamps**: decided. UTC ISO 8601 strings with milliseconds and a trailing Z (`2026-11-23T12:00:00.000Z`), always taken from the `Clock` port.
- **Not found**: a read by key returns `null`. A write to a missing record returns `not_found`. A list with no matches returns an empty list.
- **Pagination**: cursor-based with an opaque cursor. No offset pagination in the port.
- **Case and normalization**: normalize at the port (for example lowercase emails). Do not rely on the provider's collation.
- **Atomic multi-write**: expressed as a batch of operations the port runs together. Do not expose interactive transactions, because not every provider supports them. D1's current transaction support needs verifying, and this rule is the safe shape either way.
- **Constraint violations**: mapped to `conflict`.
- **Migrations**: kept in the repository. Providers define schema differently (SQL files, collection definitions), so each adapter owns its migrations. What must match across adapters is repository behavior, and the contract suite checks that. See `environments.md` section 5.
- **Queries stay inside the adapter.** Repository methods are named by intent (`findByEmail`, `listActiveByPlan`). The port has no raw query method and no generic query builder.
- **PocketBase** (an app may choose it) has its own collections, record API, and access rules. These stay inside its adapter, and repositories keep the same domain signatures. It runs as a long-lived server process with a local SQLite file, so it cannot run inside a Worker. Where it is hosted and how the web and API reach it is an app decision (verify its current deployment and backup options).

### Cache

- **Envelope, namespaced keys, miss on corrupt**: see plan section 12. The envelope is part of the port, so every adapter stores the same shape.
- **Operations**: `get(key, schema)`, `set(key, value, ttl)`, `delete(key)`, `deleteByPrefix(prefix)` if supported (capability flag).
- **Consistency**: the port documents the adapter's consistency (KV is eventually consistent). Strips that need accuracy do not use it.
- **`NullCache`** always misses and always accepts writes. Strip tests run with it.

### ObjectStorage

- **Keys** are strings with a documented prefix scheme per app. A step's manifest lists the prefixes it may touch.
- **Operations**: `get`, `put`, `delete`, `list(prefix, cursor)`.
- **Not found**: `get` returns `null`. `delete` of a missing key succeeds.
- **Metadata**: content type and size at minimum. Anything provider-specific is out of the port.

### Queue and Scheduler

- **Delivery** is at least once, so every job handler is idempotent. The port documents this, and the contract test delivers a message twice.
- **Retries and dead letters**: the port exposes retry count and a way to send a message to a failure queue.
- **Scheduler** triggers a named strip with a payload, and the stripId is created at trigger time.
- **Time limits** (when work runs on Cloudflare): work units are small. Long jobs are split into steps that enqueue the next step. Current runtime limits need verifying before the first ingest or batch strip is designed.

### RateLimiter

- **Operation**: `check(key, rule)` returns allowed or `rate_limited` with a retry-after value.
- **Accuracy**: counters need strong consistency, so they do not use an eventually consistent cache.
- **Rules** (burst and period quota) come from plan data, not from code branches.

### Payments

- **Operations**: create checkout, read subscription, cancel, refund, verify and parse webhook, send payout (capability flag).
- **Webhooks**: signature verification and idempotency are in the port. Handlers receive a parsed domain event.
- **Money**: integer minor units plus a currency code. No floats.
- **Providers**: sources describe Nigeria and Ghana as markets where Stripe operates through its Paystack network and not through standard direct Stripe accounts, so Paystack is the first adapter. Check current terms and payout support (splits, transfers) before relying on them.

### Mailer, Notifier

- **Operations**: send a templated message with a recipient and variables.
- **Result**: accepted or rejected, with a provider message ID kept for logs.
- **Test adapter** stores sent messages so strips can assert on them.

### Realtime

- **Operations**: publish an event to a channel, subscribe from a client.
- **Documented limitation**: the only planned adapter (Durable Objects) is Cloudflare-specific, so this port is the clearest case of platform lock-in. It is optional.

### Llm

- **Operations**: complete a prompt with optional context and return text plus the sources supplied.
- **Output handling**: results are data, never instructions. Apps that show model output to users decide their own disclaimers and source citation.

### Logger

- **Operations**: `log(entry)` where entry matches the shape in plan section 13.
- **Redaction** happens in the port before output.
- **Only adapter code may call `console`.**

## 5. Contract tests

For each port, `src/adapters/<port>/contract.test.ts` exports a function that takes an adapter factory and runs the same cases. Each adapter's test file calls it. Cases include:

- the documented semantics (not found, conflict, pagination, ordering),
- the error mapping table (each mapped provider failure produces the expected `ErrorKind`),
- idempotency where the port promises it,
- capability flags (cases are skipped only when the adapter declares the gap).

A new adapter is accepted when it passes the suite.

## 6. Switching providers

Steps to swap an adapter:

1. Write the adapter in `adapters/<port>/<provider>/` with its error mapping table.
2. Run the port's contract tests against it.
3. Change the adapter choice in config.
4. Cache namespaces change with the adapter, so old entries cannot be read.
5. Run the strip tests with the new config. No step or strip file changes.

If step 5 needs a step change, the port is leaking a provider detail. Fix the port and add a contract test for the case.

## 8. Adding and removing a provider

- **Add:** create `src/adapters/<port>/<provider>/` with `index.ts`, `errors.ts` and a test that runs the port's `contract.test.ts`. Add its import and entry to `src/config/registry.ts`. Name it in a profile (`src/config/profiles.ts`). Rule R44 fails if the folder and the registry disagree, and R25 fails if a profile names a missing adapter.
- **Remove:** delete the folder, its registry lines, and any profile setting that names it. Steps and strips do not change, because they only know the port.

Each port below has two or more adapters and one contract suite run against all of them. Planned adapters are not built and are never claimed as built.

|---|---|---|
| Logger | console, memory | hosted log service |
| Clock | system, fixed | |

| Database | memory, sqlite (`node:sqlite`) | PocketBase, Supabase (per app) |

| RateLimiter | memory, database (counts through the Database port) | Durable Objects |

Notes from building them:

- Adapters build errors with `portError()` because they do not know the step. The step wrapper replaces the step and strip on those errors and keeps the cause.
- `normalize: "lower"` on a database field stores the lowercased value. A field that must keep the user's casing and also be unique needs a second, normalized key field (the example `users` collection has `displayName` and `displayNameKey`).
- A log entry's `data` field holds small structured facts (such as a metric point). Redaction keeps it in every environment, so it must never hold payloads or free text.
